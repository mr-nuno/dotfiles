# Domain Entities

## AuditableEntity

```csharp
public abstract class AuditableEntity
{
    public string CreatedBy { get; set; }
    public DateTimeOffset CreatedAt { get; set; }
    public string ModifiedBy { get; set; }
    public DateTimeOffset ModifiedAt { get; set; }
}
```

- No `Id` property — each entity defines its own strongly typed ID.
- Entities that need auditing inherit from `AuditableEntity`.
- `AppDbContext` overrides `SaveChangesAsync` and automatically populates audit fields using `IDateTimeProvider` and `IUserSession`.
- On **insert**: set `CreatedBy`, `CreatedAt`, `ModifiedBy`, `ModifiedAt`.
- On **update**: set `ModifiedBy`, `ModifiedAt` only.
- Handlers **never** set audit fields manually.

## Aggregates

Folder/file layout for aggregates is defined in `.claude/conventions/dotnet.md` and
`.claude/docs/folder-structure.md` — this doc covers the `IAggregateRoot` marker and a rich root example.

The aggregate **root** is the only entity loaded/saved as a unit and the only one other
aggregates reference — **by id, never by object reference**. Mark roots with the
`IAggregateRoot` marker interface (`Domain/Common/IAggregateRoot.cs`):

```csharp
public interface IAggregateRoot;
```

## Encapsulation — No Anemic Domains

All state changes go **through the aggregate root**, never by reaching into its properties or collections:

- **Private setters.** Properties are `{ get; private set; }`, or `init` for set-once seed data. **No public setters.**
- **Behavior methods express intent and enforce invariants** — `order.AddLine(...)`, `session.End()` — not `order.Status = Shipped`. A method that can violate a business rule returns `Ardalis.Result` (`Result.Conflict(...)` for state/transition violations → handler maps to **409**; `Result.Invalid(...)` → 400). Reserve thrown exceptions for true programming errors, not expected rule violations.
- **Collections are read-only to the outside.** Expose `IReadOnlyList<T>`/`IReadOnlyCollection<T>` and mutate only via root methods. Never expose a settable or `List<T>`-typed collection that callers can mutate directly.
- **Construction** goes through a constructor (or static factory) that yields a valid root. Keep a `private`/`protected` parameterless constructor for the ORM/serializer only.
- **Handlers stay thin**: load the root, call one method, persist. Business rules live in the aggregate — never re-implemented in the handler.

## Entity Example

A rich aggregate root — private setters, intent-revealing methods, invariants enforced in the domain, read-only child collection:

```csharp
public sealed class OrderAggregate : AuditableEntity, IAggregateRoot
{
    public OrderId Id { get; private set; }
    public OrderStatus Status { get; private set; }   // an Enumeration, not a raw enum

    private readonly List<OrderLine> _lines = [];
    public IReadOnlyCollection<OrderLine> Lines => _lines.AsReadOnly();

    private OrderAggregate() { }                       // for the ORM

    public OrderAggregate(OrderId id)
    {
        Id = id;
        Status = OrderStatus.Pending;
    }

    public Result AddLine(ProductId productId, int quantity)
    {
        if (Status != OrderStatus.Pending)
        {
            return Result.Conflict("Cannot modify an order once it has left Pending");
        }

        _lines.Add(new OrderLine(productId, quantity));
        return Result.Success();
    }

    public Result Ship()
    {
        if (!Status.CanTransitionTo(OrderStatus.Shipped))
        {
            return Result.Conflict($"Cannot ship an order in state {Status}");
        }

        Status = OrderStatus.Shipped;
        return Result.Success();
    }
}
```

> The EF-mapped backing-field collection above (`_lines` + `Lines => _lines.AsReadOnly()`) is the EF Core idiom; EF maps the backing field. **Serializer-based stores (e.g. document DBs) cannot populate a private backing field** — there, expose `public IReadOnlyList<T> X { get; private set; } = new List<T>();` and mutate via the known-`List` cast instead. This is a persistence-layer detail; follow the project's data-access conventions.

## Strongly Typed IDs

Every entity uses a strongly typed ID generated by the **`StronglyTypedId`** source generator (`1.0.0-beta08`). The id lives alongside its aggregate in `Domain/{Entity}/`:

```csharp
using StronglyTypedIds;

namespace {Namespace}.Domain.Order;

[StronglyTypedId]
public partial struct OrderId;
```

(Document-database projects that use the store's native string id instead of a `StronglyTypedId` follow their own project-level convention — this is a relational/EF default.)

The source generator creates the full implementation at compile time:
- `Guid Value` property, constructor, `New()` factory, `Empty` field
- `IEquatable`, `IComparable`, `ToString()`, `==`/`!=` operators
- A nested `System.Text.Json.JsonConverter` (flat Guid serialization — no manual registration needed)

### EF Core Value Conversion

The source generator does **not** generate EF Core converters (that would require an EF Core dependency in Domain). Configure manually in `IEntityTypeConfiguration<T>`:

```csharp
// Guid-backed StronglyTypedId — value conversion only
builder.Property(p => p.Id)
    .HasConversion(
        id => id.Value,
        guid => new ProductId(guid));
```

#### Int-backed StronglyTypedId — additional configuration required

When using `[StronglyTypedId(backingType: StronglyTypedIdBackingType.Int)]`, EF Core cannot generate unique temporary keys through the value converter by default. All new entities get `Id(0)`, causing tracking conflicts when adding multiple entities in a single `SaveChangesAsync` call.

**Always configure all three**: `ValueGeneratedOnAdd()` + `UseIdentityColumn()` + `ValueComparer`:

```csharp
builder.Property(e => e.Id)
    .HasConversion(
        id => id.Value,
        value => new EntityId(value))
    .ValueGeneratedOnAdd()
    .UseIdentityColumn()
    .Metadata.SetValueComparer(
        new ValueComparer<EntityId>(
            (a, b) => a.Equals(b),
            id => id.GetHashCode(),
            id => id));
```

**Do not use `HasValueGenerator<T>()`** — it prevents EF Core from marking the property as `ValueGenerated.OnAdd` in some environments (production SQL Server vs Testcontainers), causing "temporary value" exceptions that tests won't catch.

### JSON Serialization — Flat Guid

Strongly typed IDs serialize as a **flat `Guid` string** in JSON, not as `{ "value": "..." }`. The `[JsonConverter]` attribute is generated on the struct by the source generator — System.Text.Json discovers it automatically. **No manual converter registration** is needed.

- JSON input:  `"id": "3fa85f64-5717-4562-b3fc-2c963f66afa6"`
- JSON output: `"id": "3fa85f64-5717-4562-b3fc-2c963f66afa6"`
- **Never** expose `{ "value": "..." }` in API responses.

## Enumerations

Domain enums use a hand-rolled `Enumeration` base class in `Domain/Common/` — no external dependency. Subclass enums live in their aggregate folder, `Domain/{Entity}/`.

### Enumeration Base Class

```csharp
using System.Diagnostics.CodeAnalysis;
using System.Reflection;

namespace {Namespace}.Domain.Common;

public abstract class Enumeration(int id, string name) : IComparable
{
    public int Id { get; } = id;
    public string Name { get; } = name;

    public override string ToString() => Name;

    // Compare GetType() too, so two different enumerations that share an Id are not "equal".
    public override bool Equals(object? obj) =>
        obj is Enumeration other && GetType() == other.GetType() && Id == other.Id;

    public override int GetHashCode() => HashCode.Combine(GetType(), Id);

    public int CompareTo(object? obj) =>
        obj is Enumeration other
            ? Id.CompareTo(other.Id)
            : throw new ArgumentException("Object is not an Enumeration");

    public static IEnumerable<T> GetAll<T>() where T : Enumeration =>
        typeof(T)
            .GetFields(BindingFlags.Public | BindingFlags.Static | BindingFlags.DeclaredOnly)
            .Select(f => f.GetValue(null))
            .OfType<T>();

    public static T FromId<T>(int id) where T : Enumeration =>
        GetAll<T>().FirstOrDefault(e => e.Id == id)
        ?? throw new InvalidOperationException($"'{id}' is not a valid id in {typeof(T)}");

    public static T FromName<T>(string name) where T : Enumeration =>
        GetAll<T>().FirstOrDefault(e => string.Equals(e.Name, name, StringComparison.OrdinalIgnoreCase))
        ?? throw new InvalidOperationException($"'{name}' is not a valid name in {typeof(T)}");

    // Safe parsing at boundaries (e.g. binding a request DTO string to an Enumeration).
    public static bool TryFromName<T>(string? name, [NotNullWhen(true)] out T? value) where T : Enumeration
    {
        value = name is null ? null
            : GetAll<T>().FirstOrDefault(e => string.Equals(e.Name, name, StringComparison.OrdinalIgnoreCase));
        return value is not null;
    }

    public static bool TryFromId<T>(int id, [NotNullWhen(true)] out T? value) where T : Enumeration
    {
        value = GetAll<T>().FirstOrDefault(e => e.Id == id);
        return value is not null;
    }
}
```

- Prefer an `Enumeration` over a raw C# `enum` for any domain concept that has behavior, a stable id for storage, or a bounded set you reason about.
- **API request DTOs accept the enumeration's `Name` as a `string`** and map at the boundary with `TryFromName<T>` (return 400 on miss) — never bind an `Enumeration` directly from JSON. Responses serialize the enumeration as `{ "id", "name" }`.

### Usage Example

```csharp
namespace {Namespace}.Domain.Order;

public sealed class OrderStatus(int id, string name) : Enumeration(id, name)
{
    public static readonly OrderStatus Pending = new(1, nameof(Pending));
    public static readonly OrderStatus Processing = new(2, nameof(Processing));
    public static readonly OrderStatus Shipped = new(3, nameof(Shipped));
    public static readonly OrderStatus Cancelled = new(4, nameof(Cancelled));
}
```

### Enumeration with Behavior

Subclasses can encapsulate domain logic such as state transition validation:

```csharp
public sealed class OrderStatus(int id, string name) : Enumeration(id, name)
{
    public static readonly OrderStatus Pending = new(1, nameof(Pending));
    public static readonly OrderStatus Processing = new(2, nameof(Processing));
    public static readonly OrderStatus Shipped = new(3, nameof(Shipped));
    public static readonly OrderStatus Cancelled = new(4, nameof(Cancelled));

    public bool CanTransitionTo(OrderStatus next) => (this, next) switch
    {
        _ when Equals(next) => false,
        _ when Equals(Pending) => next.Equals(Processing) || next.Equals(Cancelled),
        _ when Equals(Processing) => next.Equals(Shipped) || next.Equals(Cancelled),
        _ => false
    };
}
```

### EF Core Value Conversion

Configure manually in `IEntityTypeConfiguration<T>` — store by **Id (int)**, not by name:

```csharp
builder.Property(o => o.Status)
    .HasConversion(
        status => status.Id,
        id => Enumeration.FromId<OrderStatus>(id));
```

### EF Core Query Gotcha — OrderBy on Enumeration Properties

EF Core cannot translate member access (`.Id`, `.Name`) on value-converted properties in LINQ queries. Use the property directly — EF Core applies the value conversion automatically:

```csharp
// WRONG — EF Core can't translate .Id on a value-converted property
.OrderBy(t => t.Priority.Id)

// CORRECT — EF Core uses the configured value conversion (Enumeration → int)
.OrderBy(t => t.Priority)
```

## Ardalis Specifications

Specifications live in `Domain/{Entity}/Specifications/`. Apply directly against `DbSet<T>` using `WithSpecification()` — **no repository abstraction**.

### Naming Convention

Specifications are named `{Entity}By{Filter}Spec` or `{Entity}{Purpose}Spec`:

- `ProductByNameSpec` — filter by name
- `ProductActiveSpec` — filter active products
- `ProductWithReviewsSpec` — includes related data
- `ProductPagedSpec` — pagination specification

```csharp
public sealed class ProductByNameSpec : Specification<Product>
{
    public ProductByNameSpec(string name)
    {
        Query.Where(p => p.Name == name);
    }
}

// Usage in handler:
var product = await db.Products
    .WithSpecification(new ProductByNameSpec(name))
    .FirstOrDefaultAsync(ct);
```

- Use specifications for: queries reused across multiple handlers, complex filters/includes, and queries that benefit from encapsulation and testability.
- For **simple, one-off queries** (e.g., `FindAsync` by ID), using `IApplicationDbContext` directly is fine — don't force a specification.
